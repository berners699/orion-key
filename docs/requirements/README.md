# 需求工作流

负责人可以直接用中文描述业务场景和希望看到的结果。AI 整理需求、实施计划和验收证据。常规技术选择由 AI 处理。业务规则存在实质歧义，或涉及资金、权限、不可逆删除时，由负责人确认相关决策。

1. **理解需求**。明确使用者、业务目标、功能范围、验收结果和排除项。
2. **分析现有代码**。从路由、API、服务、数据和测试追踪既有行为及可复用入口。记录源码证据和待确认项。
3. **评估影响**。列出页面、API、历史数据、权限、外部服务和失败路径。单独识别业务决策与运行授权。
4. **制定实施计划**。使用相同的需求标识在 [docs/tasks](../tasks/README.md) 记录步骤、依赖、验收检查和回滚。
5. **实现前后端**。沿用现有分层，保持前后端类型、鉴权和错误体验一致。
6. **处理数据库变更**。记录兼容和回填。实现顺序按依赖调整，涉及迁移时在隔离环境验证。无数据库变化时注明。
7. **执行自动测试**。运行影响范围内的 lint、类型检查、构建和测试。记录实际结果、失败或环境阻塞。
8. **验收结果**。逐条把验收标准对应到测试或联调证据，区分已验证、失败、受阻及不适用。
9. **更新文档**。同步需求结论、任务结果和相关 [架构文档](../architecture/overview.md)，用中文交付。

较小需求可把目标、范围、验收和验证结果合并到任务记录或交付说明。权限、数据或资金受影响时仍须明确相关约束和验证。尚未确定的业务规则用“待确认”标记。

## 需求模板

在此目录创建 `<需求标识>.md`，关联同名任务记录。

| 字段 | 填写内容 |
| --- | --- |
| 业务目标 | 用户、问题、预期价值 |
| 功能范围 | 支持的流程、排除项和依赖 |
| 页面交互 | 页面入口、操作、成功、加载、空态、失败及移动端 |
| API 和数据模型变化 | 方法、字段、响应、状态、兼容、迁移与回滚 |
| 权限要求 | 用户、管理员、访客、数据归属及可见字段 |
| 异常情况 | 无权限、非法输入、重复操作、并发、超时及外部失败 |
| 验收标准 | 可观察、可复现的场景和预期 |
| 测试结果 | 对应的命令或联调证据、状态、缺失条件与任务记录 |
| 决策记录 | 已确认规则、负责人决定与待确认项 |
